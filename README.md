# slack-ml

Slack コミュニティのメンバー活性化のための機械学習プロダクトです。
Slack のエクスポートを DuckDB に取り込み、bronze / silver / gold の3層で整え、
「先週まで来ていたのに、これから4週間来なくなりそうなメンバー」を予測します。
予測した人には、話題の近いメンバーを「つなぐ相手」として添えます。
あわせて、チャンネルごと・人ごとに「ひとりしか答えていない」偏り（属人化）を出し、副担当の候補を選びます。
結果は CM 向けの週次レポート（HTML）と、API と Slack のスラッシュコマンドから使えます。

参考にした記事: [【保存版】データサイエンティスト転職を決めるポートフォリオのガイドライン](https://qiita.com/masso/items/44437b48706483ce9f30)

## 使い方

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

cp configs/local.example.yaml configs/local.yaml   # パスを自分の環境に合わせて書き換える

python scripts/weekly.py            # 毎週の処理（下の図）。最後にレポートのパスを表示する
python scripts/train_churn.py       # 評価だけを詳しく見る（信頼区間、特徴量の重要さ）
pytest                              # 自動テスト
```

`weekly.py` が毎週することは次のとおりです。

```
パイプライン（bronze → silver → gold、品質チェック）
  → ウォークフォワード評価でモデルを選ぶ（ops.model_evaluation）
  → 選んだモデルで今週の対象者を採点し、理由を付ける（ops.risk_scores）
  → 詳しい人探し: 索引を作り直して保存し、評価し、つなぐ相手を選ぶ（artifacts/expertise.joblib、ops.connect_suggestions）
  → 見守り: 特徴量の分布の変化と確率のずれ（ops.feature_drift、ops.calibration）
  → レポート（reports_dir/weekly.html）
```

そのほかの、使うためのスクリプトです。

| スクリプト | 内容 |
|---|---|
| `scripts/search_experts.py "質問文"` | 質問に詳しそうなメンバーを探す（名前が出るので、結果を外に貼らない） |
| `scripts/evaluate_expertise.py` | 詳しい人探しの評価（返信した人が上位 N 人に入った割合） |
| `scripts/serve.py` | API を手元で起動する（http://127.0.0.1:8000/docs に API の説明書） |
| `scripts/dependency_map.py` | 属人化マップと副担当の候補を表示する（既定では人とチャンネルを伏せる。`--names` で名前を出す） |

調べるためのスクリプトもあります。どれも読み取り専用で DWH を開き、件数だけを表示します（本文や人の名前は出しません）。

| スクリプト | 内容 |
|---|---|
| `scripts/inspect_export.py` | エクスポート（フォルダ、zip、tar.gz）の構造と件数 |
| `scripts/find_exports.py` | 展開したフォルダの中のバッチどうしの重なり |
| `scripts/profile_bronze.py` | bronze の件数、subtype、タイムゾーン、ボット |
| `scripts/profile_silver.py` | bronze との突き合わせ、投稿者の分類ごとの件数 |
| `scripts/profile_gold.py` | イベントログと週次 KPI |
| `scripts/explore_labels.py` | 離脱ラベルの定義の候補ごとの陽性の数 |
| `scripts/profile_features.py` | 特徴量とラベルの検算、離脱した人としなかった人の比較、復帰率 |
| `scripts/sql.py` | 任意の SQL を1本実行する |

`weekly.py` は、品質チェックで止まったら予測もレポートも作らずに終了コード 1 で終わります。
画面には順位と理由だけを出し、メンバーの名前はレポート（`reports_dir/weekly.html`、git の管理外）にだけ書きます。

パイプラインだけを実行するときは `scripts/run_pipeline.py`、1つの層だけを作り直したいときは、`scripts/load_bronze.py`、`scripts/build_silver.py`、`scripts/build_gold.py` を使います。

## 設計で決めたことと、その根拠

どれも、直す前にデータを数えて決めました（プロファイリングの SQL はすべて `scripts/` に残してあります）。

| 決めたこと | 根拠 |
|---|---|
| 日付は `ts` を日本時間に直して作り、日別ファイルの名前の日付は使わない | 日別ファイルは米国太平洋時間で区切られていた。4つのタイムゾーンで照合し、太平洋時間だけが全件一致した。ファイル名の日付で数えると、夏時間の切り替わる日に見かけの増減が出る |
| ボットは bot_id だけでなく、投稿者（users.json の is_bot）と subtype の3つで分類する | メッセージの4割強が1つの日報ボットの投稿だった。bot_id だけでは、メンバー名義のアプリの自動投稿と区別できない |
| メンバー名義のアプリの自動投稿は、活動に数えない | 本人が来なくなっても投稿が続き、モデルから「活動中」に見えてしまう |
| silver では行を消さずに `author_type` と `is_activity` を付ける | 分類ごとの件数を足すと bronze の件数と一致することを、品質チェックで毎回確かめられる。ボットの投稿への返信の親も探せる |
| イベントログに相手の種類（member / self / bot）を持たせる | 自分のスレッドへの返信や、日報ボットへの反応で、メンバーどうしの交流を多く見積もらないため |
| 観測しきれていない値は 0 ではなく NULL にする | KPI の端の週や、28日先までデータが無い予測時点のラベル。0 にすると「急に悪化した」ように見える |
| ラベルは「次の28日に行動（投稿、返信、リアクション）が1回も無い」 | 14日や「行動が半分以下」と件数を比べて決めた。来なくなった後に戻る人も一定数いるので、レポートでは「4週間の空白」と呼ぶ |
| 主な評価は「直近7日に行動した人」だけで行う（早期発見） | 1回の離脱は何週も続けて陽性になり、2回目以降は「最後に来てからの日数」だけで当たる。声をかけて間に合うのは1回目だけ |
| 件数ではなく割合の特徴量も入れる（`unreplied_share_28d` など） | 件数で比べると活動量と交絡し、「返信が付かなかった投稿」は離脱した人の方が少なく見えた。割合で比べると逆になった |

## 予測と評価の方法

- **予測時点**: データの最終日の翌日から7日おきに遡る。最後の予測時点（推論用）はラベルが NULL。
- **対象者**: 予測時点の直前28日に1回以上行動し、7日以上前に参加したメンバー。
- **リーク対策**: 特徴量は予測時点より前の出来事だけから作る。予測時点より後のデータを消して作り直しても、特徴量が完全に一致することをテストしている（`tests/test_pipeline.py::test_features_do_not_use_future_data`）。
- **ウォークフォワード評価**: 過去で学習して次の13週を評価する、を4回繰り返す。学習と評価のあいだは28日空ける（パージ）。
- **比べるもの**: ルール「直近28日の行動が少ない順」「最後に来てからの日数が長い順」、ロジスティック回帰、勾配ブースティング。ハイパーパラメータは調整せずに決めた値で比べる（陽性が少なく、調整すると評価期間への過学習になるため）。
- **指標**: PR-AUC、予測時点ごとの上位 K 人の適合率と再現率、リフト。差には予測時点を単位にしたブートストラップで95%信頼区間を付ける。
- **モデルの選び方**: 早期発見の PR-AUC が最も高いものを使う（ルールが最も高ければルール）。同点なら単純な方。評価の結果を見る前に決めた手続きで、結果は `ops.model_evaluation` に残す。

## 今週の予測と理由

- 選んだモデルを、ラベルのある全期間で学習し直し、最新の予測時点（データの最終日の翌日）の対象者を採点する。
- **今週声をかけたいメンバー**: 直近7日に行動した人の中で、リスクの高い順に K 人。
- **1週間以上来ていないメンバー**: 直近28日には行動したが、この1週間は来ていない人。
- **理由**: その人の特徴量を1つずつ「継続している人の中央値」に置き換えて、予測がどれだけ下がるかを測り、大きい順に3つまで出す。値が「危ない向き」（行動が少ない、最後の行動から日が空いている、など）にずれている特徴量だけを理由にし、モデルが直感と逆向きの関係を学んでいても、その向きは見せない。
- 予測は `ops.risk_scores` に予測時点とモデルごとに残す（同じ予測時点で実行し直すと置き換わる）。声をかけた人がその後戻ってきたかを、後で確かめるため。

## 詳しい人探しと、つなぐ相手

- **方法**: メンバーごとに直近120日の発言をまとめ、文字の 2〜3-gram の TF-IDF を LSA（64次元）で圧縮し、コサイン類似度で比べる。日本語の分かち書きをしなくても、「pandas」「集計」のような話題の語を拾える。
- **つなぐ相手**: 今週声をかけたいメンバーごとに、話題の近いメンバーを3人選ぶ。相手は、直近7日に行動していて、自分も声をかけたいメンバーに入っていない人から選ぶ（来なくなりそうな人どうしをつながない）。
- **評価**: 正解のラベルが無いので、「投稿に返信した人は、その話題に詳しい」とみなす。最後の8週の投稿を質問文にして、その前の発言だけで作った索引で検索し、実際に返信した人が上位 N 人に入った割合を、「発言の多い順」「ランダム」と比べる。
- 返信する人が話題よりも活発さで決まるコミュニティでは、「発言の多い順」の方が高く出る。レポートにはその比較をそのまま出す。

## 声かけの効果の確かめ方（A/B テストはやめた）

一度は、候補をメンバー単位のハッシュで「声をかける」「見守る（比較のために声をかけない）」に分ける A/B テストを作りました。次の2つの理由でやめました。

1. **比べるために、あえて支援を控える人を作ることになる。** 職場のように、困ったときに声をかけてもらえるかが働きやすさに直結する場では、受け入れにくい。
2. **結果が出るまでが長すぎる。** K が小さいと、差を見つけるのに必要な人数が集まるまで年単位かかる見込みだった。

代わりに、次の2つで確かめる方針です（まだ実装していません）。どちらもランダムに分けないので、因果の主張は A/B テストより弱くなります。そのことは結果と一緒に書きます。

- **導入前後の比較**: 使い始めた日を境に、週次 KPI（活動人数、やり取り人数、7日以内の返信率）と、「まだ来ている人が次の4週間も来続けた割合」を比べる。試験期間のような季節の影響があるので、前の年の同じ時期とも比べる。
- **段階導入**: チームごとに使い始める時期をずらし、先に使い始めたチームと、まだのチームを同じ期間で比べる。最終的には全チームが使う。

設定ファイルに `experiment:` の節が残っていると、消すように伝えるエラーで止まります。

## API と Slack

```bash
SLACK_ML_API_KEY=好きな文字列 python scripts/serve.py
curl -H "X-API-Key: 好きな文字列" "http://127.0.0.1:8000/v1/risk?limit=5"
curl -H "X-API-Key: 好きな文字列" --get --data-urlencode "q=pandas で集計" http://127.0.0.1:8000/v1/experts
```

| エンドポイント | 内容 | 認証 |
|---|---|---|
| `GET /health` | 動いているかの確認 | なし |
| `GET /v1/risk?limit=5` | 今週声をかけたいメンバー、理由、群、つなぐ相手 | API キー |
| `GET /v1/experts?q=…&limit=5` | 質問文に詳しそうなメンバー | API キー |
| `POST /slack/commands` | `/slackml risk`（CM だけ）、`/slackml experts 質問文` | Slack の署名 |

秘密の値は環境変数で渡し、設定ファイルやコードには書きません。

| 環境変数 | 内容 |
|---|---|
| `SLACK_ML_API_KEY` | API キー。設定されていなければ、API は 503 を返す |
| `SLACK_SIGNING_SECRET` | Slack アプリの Signing Secret。設定されていなければ、Slack のコマンドは 503 を返す |
| `SLACK_ML_CONFIG` | 設定ファイルのパス（既定 `configs/local.yaml`） |

Slack から使うときの準備:

1. Slack アプリを作り、Slash Commands に `/slackml` を追加する。Request URL は「公開された URL/slack/commands」。
2. Basic Information の Signing Secret を `SLACK_SIGNING_SECRET` に設定する。
3. `/slackml risk` を使える CM の user_id を、設定の `slack.manager_user_ids` に書く。

Slack は3秒以内に応答が無いとエラーにするので、「受け付けました」をすぐに返し、結果はあとから response_url に送ります。
結果は本人にだけ見える形（ephemeral）で返し、メンバーの名前やリスクをチャンネルに流しません。

Docker で動かすときは、手元で `weekly.py` を実行して作った DWH と索引をマウントします（DWH は読み取り専用で開きます）。

```bash
docker build -t slack-ml .
docker run --rm -p 8000:8000 -v "$(pwd)/data/real:/data" \
  -e SLACK_ML_API_KEY=… -e SLACK_SIGNING_SECRET=… slack-ml
```

コンテナは root ではないユーザー（uid 10001）で動きます。`configs/docker.yaml` は `/data/warehouse.duckdb` と `/data/artifacts` を読みます。

## モデルの見守り

- **特徴量の分布の変化（PSI）**: 学習に使ったデータ（ラベルのある全期間）の十分位で区間を切り、今週の対象者と区間ごとの割合を比べる。NULL は別の区間として数える（取り込みの不具合で値が欠けたときに気付ける）。0.1 未満は安定、0.25 を超えると大きく変化。参加してからの日数のように時間とともに必ず増えるものは「想定どおり」とする。
- **確率のずれ**: ウォークフォワード評価の予測を10の区間に分け、予測の平均と実際に来なかった割合を比べる。ECE（区間ごとのずれを人数で重み付けした平均）と、Brier スコアを「全員に平均の離脱率を言ったとき」と比べて出す。ルールは確率を出さないので測らない。
- 毎週の結果は `ops.feature_drift` と `ops.calibration` に残り、レポートの「モデルの見守り」に出る。

## 属人化マップと副担当の候補

- **答えが付いたスレッド**: メンバーのトップレベルの投稿に、ほかのメンバーが返信したもの（自分のスレッドへの書き足しは数えない）。直近90日を見る。
- **属人化**: あるチャンネルで、答えが付いたスレッドの半分より多くに「その人しか答えていない」。答えが付いたスレッドが5件以上のチャンネルだけを判断する。割合は半分以下でも、ひとりで答えた件数が10件以上のチャンネルは「件数が多い」として別に示す。
- **人ごとの負担**: 人ごとに「ひとりで答えたスレッド」の合計（その人が休むと答えが付かなくなる数）と、全体に占める割合を出す。チャンネルごとに見ると一番ではなくても、合計すると負担の大きい人が分かる。
- **副担当の候補**: そのチャンネルで発言していて、直近28日に行動した人から3人まで選ぶ。すでに担当者として負担のある人と、ひとりで答えた件数がもっと多いチャンネルで候補になっている人は後ろに回す（同じ人に集めない）。
- 結果は `gold.thread_responses`、`gold.channel_dependency`、`gold.person_dependency`、`gold.backup_candidates` に残り、`scripts/dependency_map.py` で表示する。属人化かどうか、副担当を誰にするかは人が判断する。
- DM、非公開チャンネル、口頭のやり取りは見えない。「了解です」のような短い返信も答えに数える。

## テストと CI

```bash
ruff check src scripts tests
pytest
```

テスト用のデータ（`tests/conftest.py`）は、実データの癖を決まった規則で再現した小さなエクスポートです。
太平洋時間のファイル、2つのバッチへの同じメッセージの重複、日報ボット、メンバー名義のアプリ投稿、翌日に付く返信、途中で来なくなるメンバーを含みます。
実データを使わないので、GitHub Actions でもそのまま動きます。

テストが本当にバグを見つけられるかは、コードをわざと壊して確かめました（未来の返信を数える、予測時点の当日を含める、重複を除かない、CASE の判定順を入れ替える）。どれもテストが失敗します。

## プライバシー

- 実データと実データの置き場所（`data/`、`configs/local.yaml`）は git の管理外。
- 調査のスクリプトは件数だけを表示し、人の名前は SQL の中で伏せる。
- オプトアウトしたメンバーは、取り込みの時点で除外する（`privacy.exclude_users`）。

特定の人を外す方法は2つあります。どちらも `configs/local.yaml` に Slack の user_id を並べます。

| 設定 | 何が起きるか | 使う場面 |
|---|---|---|
| `privacy.exclude_users` | 取り込みの時点で、その人の投稿・返信・リアクションを丸ごと落とす。ほかの人の分析にも影響する（その人からもらった返信やリアクションが消える） | 本人がデータの利用を断った（オプトアウト） |
| `model.exclude_from_scoring` | データは残し、今週の予測の対象からだけ外す。声をかけたいメンバーの一覧、レポート、API、つなぐ相手の候補に出なくなる。学習データと属人化マップには残る | 部署長や退職済みの人など、声をかける対象ではない人 |

## 分かっている限界

- Slack からリアクションを付けた時刻が取れないので、対象の投稿の時刻で近似している。予測時点より後に付いたリアクションが、特徴量にわずかに混ざる可能性がある。
- channels.json と対応がとれないチャンネルがある（プライベートチャンネルか、名前の変更や削除の可能性）。
- 読むだけのメンバーはデータに現れない。「投稿もリアクションもしない」を離脱と定義している。
- 信頼区間は予測時点を単位にしているので、同じメンバーが何週も続けて出てくることによるつながりは残る。
- 詳しい人探しの評価は「返信した人 = 詳しい人」という代わりの正解を使っている。返信は話題よりも活発さで決まることがある。
- 声かけの効果は、まだ測っていない。導入前後の比較と段階導入で確かめる方針だが、ランダムに分けないので因果の主張は弱い。
- 理由は1つずつ置き換えて測るので、相関の強い特徴量（行動数と活動日数など）は、片方を置き換えても、もう片方がリスクを支えて小さく出る。
- ワークスペースは1つだけ。

## この先にやれること

- 確率のずれが大きいときに、確率を補正する（`CalibratedClassifierCV` の isotonic など。評価期間とは別の期間で補正する）
- 分布が大きく変わったときに、学習に使う期間を直近に絞る（直近の何週で学習すると評価が良いかを、ウォークフォワードで比べる）
- `weekly.py` を cron やワークフローで毎週自動で実行し、品質チェックで止まったら通知する
- 副担当の候補を選ぶときに、担当者になっていなくても、人ごとの負担（ひとりで答えた件数の合計）が大きい人を後ろに回す
- 属人化マップで、「了解です」のような短い返信を答えに数えない
